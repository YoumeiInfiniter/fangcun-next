# Fangcun EP001 三方对照诊断报告

> 对照对象：小说原文第一章、Fangcun Skill 输出 EP001、编剧确认版第1集  
> 分析日期：2026-08-08  
> 目的：定位内容、台词、因果、忠实度和格式差距，并追溯到当前 Skill 的可能原因。  
> 限制：本轮尚未取得该集对应的改编指引、故事骨架和集纲，因此可以判断“剧本对原文”的差距，但暂时不能最终判断“剧本是否执行了集纲”。

## 1. 总结结论

这份样本中，Fangcun 的主要问题不是完全没读原文，也不是大规模凭空另写故事，而是：

> 它把原文压缩成了“情节点 + 热门金句”的骨架，删掉了台词之间的问答关系、人物为何作出反应的依据，以及笑点成立所需的铺垫。

所以 Skill 版从事件列表看基本正确：三亿离婚、穿成恶毒原配、996 出现、强行绑定、牵手任务、雷劈谢淮舟、发现绑错对象都在。但从一场戏看，人物不是在互相作用，而是在轮流说信息。

编剧版的核心价值，是重新补回了四类“桥梁”：

1. 观众理解世界观的桥梁：退休、穿书、原主结局、为什么在恋综前离婚。
2. 谢淮舟听见系统的桥梁：听见声音、判断叶聆还在做梦、公开宣誓绝不会爱她。
3. 喜剧台词的桥梁：系统先说完整上句，叶聆再接反向下句。
4. 雷击的因果桥梁：拒绝爱上叶聆 → 任务出现 → 明确失败 → 惩罚错位。

不过，编剧版也不是可以直接变成系统格式标准的完美样本。它包含少量无原文依据的新设定，以及与当前 Fangcun validator 不兼容的 Markdown、场次标题和 OS/VO 写法。

## 3. 三版整体比较

| 维度 | Fangcun Skill 版 | 编剧确认版 | 判断 |
|---|---|---|---|
| 主事件覆盖 | 主要节点基本保留 | 主要节点保留，并补充背景 | 两版都没有换掉主事件 |
| 原文忠实度 | 中等：大量压缩，新增少量动作/反应 | 较高：保留更多原文台词，但也新增视觉设定 | 编剧版更接近原文的完整语义 |
| 因果关系 | 弱：多个反应缺少前置原因 | 较强：补回听见系统、误判、宣誓、受罚 | 这是两版最大的质量差距 |
| 台词连接 | 弱：保留下句但删除上句，容易像网络梗拼接 | 较强：多数台词形成 setup → response → payoff | 编剧版笑点更成立 |
| 人物声音 | 叶聆有少量原文金句；谢淮舟和996较扁 | 三人声音明显分开 | 编剧版更能遮名识人 |
| 信息可理解性 | 没读原著的观众较难快速理解穿书和听声机制 | 闪回、VO、OS 补足首集信息 | 编剧版更像首集而非梗概 |
| 视听化 | 基础动作，有少量不可解释反应 | 闪回、快切、卡通小人、光团动作较丰富 | 编剧版更有画面，但要验证制作可行性 |
| 节奏 | 很快，但快到省略逻辑 | 信息密集，较完整，但可能偏长 | 需要以公司真实时长标准校准 |
| 格式 | 更接近当前机器 validator | 更接近编剧日常稿，但不符合当前机器规则 | 暴露“机器格式”和“业务格式”不是一套标准 |

## 4. 逐段差距分析

### 4.1 开场：冲突保留了，但人物调度是无依据补写

Fangcun 增加了“叶聆拉着行李箱进门”“谢淮舟把合同推到面前”。原文只提供离婚话语，没有行李箱和合同动作。

这些不属于重大改编，但存在两个问题：

- 行李箱没有在后续继续发挥作用，像 Prompt 中“动作是因、对话是果”的通用示例被机械套入；
- “指尖悬在半空”没有明确悬在哪里、准备做什么，只是泛化震惊动作。

编剧版改为“将协议扔在地上”，同样是补桥，但作用更明确：它把谢淮舟的冷硬态度变成可见动作，并直接服务离婚冲突。

结论：补写动作不是问题，问题是动作是否改变人物关系、推动下一句台词。Skill 版动作更像装饰，编剧版动作更像戏剧行为。

### 4.2 穿书背景：Skill 版只有结论，编剧版展示了认知过程

Skill 版用一句 OS 概括：“刚退休回来享福，结果成了恶毒原配。”

它说明了结果，却没有让观众知道：

- 她刚完成任务；
- 她为什么期待享福；
- 原主为什么要离婚；
- 原主会得到什么结局；
- 三亿为什么对现在的叶聆如此重要。

随后谢淮舟突然说“你当众伤人，集团损失很大”，这是一句把原文内心理由改成角色口头说明的台词。它有信息，但说话目的弱：谢淮舟已经提出离婚，此时又向叶聆复述她自己做过的事，接近“给观众念背景”。

编剧版用“两分钟前”闪回、婚礼照和死亡蒙太奇，把同样的信息拆成可见画面，再用叶聆“我的三亿呢”完成情绪落点。它不只是信息更多，而是让信息最终落到人物欲望上。

### 4.3 996 登场：Skill 版删除了角色声音

原文给996安排了一长串押韵式登场词，这是系统“吵、蠢、过度热情”的声音识别码。

Skill 版只剩“炮灰自救系统996号为您服务”，然后立刻进入功能说明。结果996从一个有喜剧人格的角色，变成了普通任务播报器。

编剧版保留押韵登场词，并给光团加入豆豆眼、转圈、发抖等动作，系统人格因此更清楚。

### 4.4 “什么b动静”：Skill 保留了金句，却删掉金句的响应对象

原文结构是：

`996大段热情登场 → 谢淮舟疑惑谁在说话 → 叶聆嫌吵，问“什么b动静” → 996认真纠正“我不是b动静”`

Skill 版变成：

`996报名字 → 叶聆说“什么b动静” → 996说自己是高级AI`

“什么b动静”还在，但它不再是对突如其来大段噪声的吐槽；996也没有接住“我不是b动静”的包袱。它从对话变成了一条孤立网络梗。

编剧版恢复了完整响应关系，所以笑点成立。

### 4.5 “吃不完的苦”：典型的只留 punchline、不留 setup

Skill 版中，996直接讲“要经历被打脸、被误会、被虐身、被离婚等九九八十一难”，叶聆随后说“吃不完的苦”。

但原文真正的梗是：

`996：被虐没关系，吃得苦中苦，你就能得到——`

`叶聆：吃不完的苦。`

笑点依赖996主动留下句式空位，叶聆抢答反转。Skill 版删掉上句，却保留下句，导致“吃不完的苦”语法上还能看懂，戏剧上却没有被触发。

编剧版恢复了这组 setup/punchline。

### 4.6 谢淮舟为什么能听见：Skill 版缺少全剧核心规则

Skill 版让996在空中出现、让谢淮舟说“……我吗”，但没有清楚建立：

- 谢淮舟可以听见系统；
- 996声称只有纯正恋爱脑才能听见；
- 谢淮舟把系统信息理解为叶聆仍想攻略自己。

“……我吗”因此像突然插入的反应。观众可能不知道他听见了多少，也不知道他是在回应谁。

编剧版加入谢淮舟 OS“什么声音？谁在说话？”和“原来叶聆还在做梦”，补回了男主认知链。这对后续通感和自我攻略非常重要。

### 4.7 “绝不爱上叶聆”：Skill 删除了雷击前最重要的喜剧铺垫

原文在系统任务前，让谢淮舟明确发誓：“就算从这里跳下去，死外边，也不可能爱上叶聆。”

这句话同时完成：

- 男主人设；
- 当前关系；
- 恋爱脑系统对他的讽刺；
- 下一秒被雷劈的反差铺垫；
- 后续“真香”长线。

Skill 版把它全部删掉，任务直接出现。雷击仍然是事件，但少了“刚立 flag 就遭报应”的喜剧价值。

编剧版把这句内心誓言转成口头台词，戏剧作用明显增强。是否应公开说出口，可以继续优化，但保留这个 beat 是正确的。

### 4.8 结尾“死我”：Skill 改错了时序和情绪

原文中的“死我”是叶聆在雷击前说“你有本事就劈……死我”时被突发事件打断的尾音。看到谢淮舟倒下后，她的反应是震惊。

Skill 版却写成：

- 996已经承认绑错；
- 叶聆嘴角翘起；
- 叶聆再说“……死我”。

这里存在三个问题：

1. 台词从被打断的前句残片，变成了事后独立台词，语义失去来源；
2. “嘴角翘起”把两小时后叶聆发现好处时的兴奋提前了；
3. 原文此刻的震惊被改成幸灾乐祸，人物反应时序失真。

这是本集最明确的原文忠实度错误，也是用户所说“部分台词连接不上”的直接实例。

编剧版让叶聆瞪大眼睛，并以996承认绑错收尾，时序更准确。

## 5. Fangcun 台词问题的本质

### 5.1 不是单纯“台词短”，而是对话配对被拆散

一段有效对话通常包含：

`刺激 → 理解 → 反应 → 对方再反应 → 结果`

Skill 版经常只保留刺激和一句记忆点台词，中间理解过程被删掉。因此每句单看都像短剧台词，连起来却不像人在对话。

### 5.2 过度保留金句，反而伤害金句

“什么b动静”“再吵自鲨”“吃不完的苦”“不是哥们等一下”“死我”都来自原文。但保留原句不等于忠实：若上句、说话对象和发生时机改变，原句也会变成错句。

### 5.3 谢淮舟没有完整的认知链

Skill 版的谢淮舟主要承担：宣布离婚、解释当众伤人、说“我吗”、被雷劈。他没有经历“听见怪声 → 判断系统内容 → 认为叶聆仍迷恋自己 → 立 flag”的过程，所以男主更像剧情工具。

### 5.4 996被功能化

Skill 版996负责说明规则，没有保留足够的自恋、热情、笨拙和与叶聆互怼的性格。台词因此“正确但简陋”。

### 5.5 叶聆只剩几个网感梗，缺少稳定欲望

原文叶聆在本场的核心驱动力不是单纯摆烂，而是“刚退休要享福，却失去三亿并面对死亡结局”。编剧版用“我的三亿呢”把欲望钉住；Skill 版一闪而过，导致她后续躺平和反系统更像人设标签，而不是处境驱动。

## 6. 编剧确认版做对了什么

1. **把首集必要信息视觉化**：纯白空间、退休礼花、婚礼照、死亡蒙太奇。
2. **保留了系统和叶聆的完整对话接力**，不只摘金句。
3. **让谢淮舟进入系统规则**，而不是站在旁边等待被劈。
4. **恢复“绝不爱她 → 马上受罚”的 setup/payoff**。
5. **用动作区分三个人物声音**：叶聆小人、996光团、谢淮舟冷眼。
6. **正确处理结尾情绪**：先震惊，再由系统承认错误卡断。

编剧版反映出的隐性业务标准是：

- 首集必须让没看过小说的人理解核心设定；
- 喜剧台词不能只留梗，必须保留上句和反应；
- 关键系统规则要通过人物当场反应证明；
- 主角的核心欲望要落在可记忆台词上；
- 集末反转前必须有铺垫，而不是只放结果。

## 7. 编剧确认版仍需注意的问题

### 7.1 “完成1000个快穿任务”没有原文依据

原文是“做完最后一个攻略任务，从快穿局退休”，没有1000个任务。这个改动强化了资历，但属于新增事实。若后续人物能力、年龄感或历史任务被引用，就会形成新的连续性负担。

### 7.2 “只有纯正恋爱脑才能看到我”改变了原文规则

原文是“只有纯正的恋爱脑才能听见我的声音”。编剧版随后又让谢淮舟问“什么声音？谁在说话”，说明剧情实际仍依赖“听见”。这里应统一为“听见”，否则系统可见性和通感规则会冲突。

### 7.3 “吐血倒地、死不瞑目”是新增死亡画面

原文只说明最终死无全尸，没有在此明确吐血死亡。作为蒙太奇可以服务视听化，但应标记为载体适配，而不是原文事实。

### 7.4 卡通小人是有效创意，但需要成为项目级视觉规则

编剧版多次使用叶聆小人和卡通化表达。这很适合沙雕题材，但必须确认：

- 是否每集都使用；
- 是后期动画、贴纸还是AI特效；
- 是否只有内心戏出现；
- 真人叶聆与小人台词如何区分。

否则下一集模型可能忘记，或过度使用。

### 7.5 996“消失”后继续说话，需要明确声画状态

编剧版写“996消失”，随后996继续倒计时。若含义是光团消失、系统声仍在，应明确写成“光团隐去，机械音仍在脑中响起”。

### 7.6 信息密度可能超过两分钟，需要真实读速验证

编剧版比 Skill 版完整得多，但包含闪回、VO、系统长台词、多轮互怼和雷击。最终是否能在两分钟内完成，不能只按字符数判断，应该通过演员读本或 TTS 时长验证。

## 8. 格式问题分析

### 8.1 当前存在至少三套 OS/VO 格式

| 来源 | 写法 |
|---|---|
| Fangcun Skill 输出 | `叶聆OS：...` |
| 编剧版 | `叶聆（OS）：...`、`叶聆（VO）：...` |
| `script_local.md` 格式说明 | `OS（叶聆，情绪）：...`、`V.S.（叶聆，情绪）：...` |

这三种写法不兼容。更严重的是，Prompt 把 OS 定义为画外音/内心，把 `V.S.` 定义为 Voice over，而代码 validator 又主要识别“角色名+VO/OS”的形式。

因此格式问题不能归因于编剧没有遵守规则；当前系统自己就没有唯一格式。

### 8.2 场次标题不一致

当前机器门禁要求类似：

`1-1　谢家书房　夜　内`

Skill 版符合这一形式。编剧版使用：

`**1-1 谢家书房-夜-内**`

它包含 Markdown 粗体和连字符，按当前 validator 会被视为旧格式或无法识别。

需要业务确认：编剧版是公司正式规范，还是该老师个人习惯。最终只能保留一套标准，Prompt、validator、飞书展示和人工上传必须全部一致。

### 8.3 `<scriptItem>` 是机器传输壳，不应和业务剧本格式混为一谈

Skill 版要求 `<scriptItem>` 包裹；编剧终稿没有。若业务人员阅读的是飞书文档，XML 更像内部传输协议，不应成为专业剧本正文的一部分。

当前系统把“模型返回协议”和“最终剧本文档格式”绑定在一起，造成：

- 编剧手工上传的专业稿无法通过机器门禁；
- 机器稿能通过，但正文带有业务不需要的 XML；
- 修改文档时容易破坏标签，导致整个文件判失败。

### 8.4 Skill 版自己也违反了“XML外禁止文字”

Skill 输出在 `</scriptItem>` 之后附带 `<!-- 技能:钩子 ... -->` 注释，而当前运行 Prompt 明确要求 XML 外不得有任何文本。这是 Prompt 历史版本叠加留下的冲突。

### 8.5 编剧版的 Markdown 加粗和闪回标记需业务定版

编剧版使用：

- `**场次标题**`；
- `**△** **【插入闪回】**`；
- `【闪回结束】`；
- 角色名后附加 `【角色-身份】`。

这些写法人眼可读，但不一定适合解析、自动校验或后续分镜。必须决定哪些属于最终剧本规范，哪些只是飞书编辑习惯。

## 9. 根因定位

### 9.1 本样本不是“原文没有送到模型”导致的

原文第一场到绑错对象约1680字，位于第一章开头。当前单章原文采样上限约2500字，足以覆盖本集核心段落。

因此 EP1 的主要问题不是源文本截断，而是模型如何在多个相互竞争的规则中选择内容。后期剧集仍可能受章节映射和截断影响，但不能用它解释本次首集问题。

### 9.2 600–700字目标迫使模型进行超过一半的压缩

原文核心场约1680字，Skill 稿目标只有600–700字，同时还要包含动作、场次标题、系统规则和集末钩子。模型只能大规模删减。

Prompt 虽然写着“不能因压缩删掉关键台词”，同时又要求：

- 第一场不要交代太多信息；
- 单句尽量/必须不超过20字；
- 所有功能性内容尽量压缩；
- 用一句话解决三句台词；
- 每个镜头都必须推进剧情；
- 短、密、紧；
- 3秒、15秒、45秒节奏。

模型最后选择保留最醒目的名词、任务和金句，删除认知过程。这正是 Skill 稿“信息点对、对话却断”的生成机制。

### 9.3 所有 craft 被全量加载，压缩规则不会真正“按需”

代码虽然写“只加载本集需要的技能”，实际会遍历并拼接所有 craft 文件。Compress、Hook、Reversal、Satisfaction、Abuse 等方法同时进入每一集上下文。

对这类靠连续吐槽和人物反应成立的喜剧场景，过高的压缩与钩子压力会伤害对话节奏。

### 9.4 缺少结构化“不可删除因果桥”

Prompt 声称 Episode Contract 是事实源，但运行时传入的是从 Markdown 集纲中脆弱提取的片段，没有结构化声明：

- 谢淮舟必须先听见系统；
- 必须说明为什么能听见；
- 必须保留“绝不爱她”的 flag；
- “吃不完的苦”必须与上句成对；
- “死我”是被打断的尾句，不能后置。

没有这些 contract，模型会把它们当成可压缩细节。

### 9.5 AI 审核根本没有收到原文

当前 `review_script_draft()` 的输入只有：

- 集纲片段；
- 上一集剧本；
- 连续性状态；
- 当前草稿。

它没有原文摘录、事件表和改编策略。即使审核 Prompt 要求检查“是否有更好的原著台词”，Reviewer 也没有证据可比。

因此它很难发现：

- 系统听声规则被删；
- “绝不爱她”被删；
- “死我”被移动；
- 叶聆的震惊被改成微笑。

### 9.6 自动重写同样没有收到原文

`rewrite_script_draft()` 也只接收审核报告、集纲、上一集、连续性和旧草稿。第一次审核没发现原文问题，重写就只能在旧稿内部润色，无法真正回到原文修复。

这可以解释为什么多轮迭代仍可能反复出现同类问题。

### 9.7 validator奖励“格式合格”，无法判断对话是否接得上

当前确定性门禁能检查：

- XML标签；
- 分集标题；
- 场次标题；
- △动作；
- 字数；
- 场景key。

但不能检查：

- 台词是否回答上一句；
- punchline是否保留setup；
- 角色是否有理由知道当前信息；
- 因果桥是否缺失；
- 原文台词是否被错位使用。

所以 Skill 版更容易通过机器门禁，而编剧版虽然内容更好，反而可能因粗体、场次标题和无XML被拒绝。

### 9.8 “小说仿写遗留污染”不是这份样本的首要直接证据

当前 Writer Prompt 实际已经多次强调原著优先、禁止无依据原创。这说明旧小说仿写逻辑并不是以一条明显指令直接要求 Writer 自由仿写。

但遗留影响仍可能存在于：

- 旧流程顺序没有彻底迁移；
- adaptation Prompt 鼓励强化、重构和创新；
- 旧版/新版 script Prompt 共存；
- 通用 writing-methods 中仍有“第一场必须看出不是原著世界”等适用于身份重构的规则；
- 同名 Prompt 和子技能互相遮蔽。

对本 EP1 而言，更直接的根因是过度压缩、缺少 Episode Contract、审核没有原文和格式契约冲突。是否还有上游仿写污染，需要拿到本集集纲和改编指引后判断。

## 10. 本样本对新版需求的直接启示

以下不是最终技术方案，而是从已确认差距中提取出的业务要求：

1. **事件保留不等于忠实**：必须保留事件之间的因果和人物认知变化。
2. **原文金句必须连同对话功能一起保留**：不能只摘 punchline。
3. **每集必须有不可删除 beat 清单**：尤其是规则建立、人物 flag、反转铺垫和反应。
4. **首集需要单独标准**：它承担世界观、人物欲望、关系和核心机制建立，不能套普通集压缩率。
5. **Reviewer和Rewriter必须看到与Writer相同的原文依据**。
6. **人工确认版必须成为新的正式事实源**：其新增视觉规则、人物说法和系统机制要影响后续集。
7. **机器传输格式与业务剧本格式必须分离**。
8. **公司必须提供一份唯一格式样稿**：Prompt、validator、飞书和人工上传共同遵循。
9. **时长应以真实读本验证**：字符数只能作为预估，不可同时存在150字/分钟、500字/分钟和600–700字等多个标准。

## 11. 下一步需要的证据

最有价值的下一份材料，是这一集生成时实际使用的“集纲/故事骨架分集信息”。拿到后可以回答：

1. 这些因果桥在集纲中已经存在，但 Writer 删除了；
2. 还是集纲本身就只列了情节点，没有规定人物认知和台词关系；
3. Skill 稿新增的行李箱、合同、微笑等来自集纲、改编策略还是 Writer 自由发挥；
4. 编剧版修改后，哪些变化应该回写到集纲和后续连续性状态。

第二份重要材料是公司认可的标准剧本格式样稿，用于确定场次标题、人物列表、OS/VO、闪回、角色标签、Markdown粗体和XML外壳的最终规则。
