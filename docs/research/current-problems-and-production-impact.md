# Fangcun 当前问题与真实生产影响报告

> 基线版本：`fangcun-v2-dev`  
> 分析日期：2026-08-08  
> 报告用途：作为后续业务需求访谈、架构重构和效果评测的共同底稿；本报告暂不直接给出最终优化方案。

## 1. 执行摘要

Fangcun 当前已经不是一个单纯的“写剧本 Prompt”，而是由 Skill 路由、Python pipeline、Prompt 体系、文件状态、审核门禁、项目 Rules、剧本批次和飞书交付组成的混合生产系统。

它当前最成熟的部分是：

- 草稿与正式剧本分离；
- 单集审核、重写、PASS、批次提升；
- 状态持久化与断点续传；
- 剧本格式、分场和连续性等确定性门禁；
- 本地资产登记、版本保留和飞书项目目录建设。

它当前影响效果和生产稳定性的核心，不是单一模型能力不足，而是五类结构性问题：

1. **流程没有唯一真相**：根 Skill、Drama Skill、Python 主流程和状态机定义了不同的阶段顺序。
2. **模型拿到的当前集上下文可能不正确**：事件表、原文片段和集纲片段存在截断、错配或提取失败。
3. **所谓多 Agent 尚未形成真实运行隔离**：多个 Agent 文件主要是角色说明，实际仍由单体 pipeline 直接调用模型。
4. **Prompt、业务规则和校验器互相冲突**：模型可能按一份规则正确输出，却被另一份规则判错。
5. **创作流程和飞书交付没有形成一个事务闭环**：本地完成、在线文档完成、群内回贴成功是三个可能分离的状态。

因此，当前版本在小规模、人工紧密盯场的项目中可能可用，但项目变长、团队角色增多、修改轮次增加或同时运行多个项目后，会显著放大以下问题：

- 剧本偏离原文或集纲；
- 人物知情时间线与行为动机断裂；
- 后期集数质量下降；
- 编剧需要重复解释同一要求；
- 已否决版本继续污染下游产物；
- 本地和飞书版本不一致；
- 返工、等待和 token 成本无法准确归因。

## 2. 报告证据等级

为了避免把代码推断误当成真实业务事实，报告采用三个证据等级：

| 标记 | 含义 | 使用方式 |
|---|---|---|
| C：代码确认 | 已从当前代码、Prompt、状态机或测试中直接确认 | 可以直接进入技术整改清单 |
| R：生产风险 | 代码问题在真实生产中大概率造成的后果 | 需要结合项目案例判断频率和损失 |
| B：业务待确认 | 仅靠代码无法判断，必须由实际使用者补充 | 后续需求访谈逐项核实 |

本报告没有对真实剧本成片效果做盲评，也没有使用历史项目统计数据。因此，“发生频率、平均返工时间、首轮通过率、成本损失”等尚不能给出可靠数字。

## 3. 当前系统的真实运行结构

当前系统可拆成七层：

| 层级 | 主要文件/组件 | 实际职责 |
|---|---|---|
| 触发与业务规则层 | 根 `SKILL.md` | 识别用户意图、规定飞书流程、人工确认和业务红线 |
| 操作说明层 | `skills/drama/SKILL.md` | 提供 CLI、阶段说明、人工操作和异常处理指导 |
| 编排层 | `pipeline.py` | 真实阶段调度、模型调用、审核、脚本批次和导出 |
| 创作层 | `prompts/*.md`、`prompts/craft/*.md` | 规定事件提取、需求、骨架、改编、剧本和审核方法 |
| 状态与资产层 | `state.json`、`_cache/`、`drafts/`、`scripts/`、`reviews/` | 充当阶段间数据接口和持久化记忆 |
| 确定性质量层 | `agent_tools.py` 及 guardrails | 格式、分场、摘要、连续性等机器校验 |
| 交付层 | `build_feishu_project.py`、`feishu_project_executor.py` | 在线文档、项目目录、表格、版本和链接交付 |

需要特别说明：`agents/*.md` 中虽然定义了 drama-director、event-extractor、script-writer、quality-supervisor 等角色，但当前运行代码没有真正创建或调度这些独立 Agent。实际生产仍以 `pipeline.py` 的直接模型调用为主。因此目前是“多角色 Prompt 设计”，不是严格意义上的多 Agent 工作流。

## 4. 真实生产流程逐阶段影响

### 4.1 项目初始化与项目绑定

#### 当前设计

用户在飞书群触发 Fangcun 后，系统按群名创建或复用项目文件夹、表1、表2，并生成项目配置。

#### 已确认问题

1. **初始化模板和 pipeline 必填项不一致（C）**  
   `fangcun.py` 创建的模板缺少 `source_dir`、`project.paywall` 和 `project.aspect_ratio`；paywall 被放在顶层对象，而 pipeline 要求它位于 `project` 内。

2. **默认剧本批次不一致（C）**  
   根规则和多数流程默认每批 5 集，但 launcher 的 `--batch-size` 默认是 3。

3. **项目 ID 推导可能退化为 `output`（C）**  
   正式目录是 `<project>/drama/output`，而部分代码只识别目录名为 `drama` 的情况；若没有显式 `project_id`，多个项目可能得到同样的统计归因。

4. **飞书表1初始化行与根 Skill 规范不同（C）**  
   根规则要求第3行是剧名、第4行是原文；执行器额外插入 `chat_id`，使后续行整体后移。

#### 生产影响

- **假成功启动（R）**：用户看到“项目初始化完成”，但真正运行 pipeline 时才因配置缺失停止。
- **人工补配置（R）**：运营或技术人员需要进入 JSON 手工调整，破坏“业务侧不见 CLI”的目标。
- **项目归因混乱（R）**：token、资产、错误日志或飞书同步可能被记到错误项目。
- **自动化接线不稳定（R）**：Jingwei 或其他下游流程如果依赖固定表格行号，可能读取错位。

#### 业务待确认

- 当前项目初始化由谁触发：编剧、制片、运营还是技术人员？
- 初始化失败时，实际由谁补配置？平均会等待多久？
- 表1是否有其他机器人或人工流程依赖固定行号？

### 4.2 原文归档、拆章与事件提取

#### 当前设计

原文先归档到飞书，再拆分为章节文件；事件提取为后续所有创作阶段提供共同事实源。

#### 已确认问题

1. **章节读取没有按 `chapter_range` 过滤（C）**  
   `get_source_chapters()` 会读取章节目录中所有 `.txt` 文件。

2. **每章只读取前 4000 字用于事件提取（C）**。

3. **每章产出一个事件摘要，而不是多个可追溯事件（C）**。

4. **“前两章滑窗”在首次并行运行时基本不成立（C）**  
   所有章节任务同时提交，worker 主要只能看到运行前已经存在的事件，而不是刚刚按顺序完成的前两章事件。

5. **事件缺少精确原文证据位置（C）**  
   当前事件主要保存章节号和摘要，没有稳定的原文 span、关键台词位置、状态变化和因果边。

#### 生产影响

- **章节后半段关键事件丢失（R）**：反转、人物决定、关键台词若出现在长章节后半段，可能根本没有进入事实源。
- **次级事件消失（R）**：一章中的人物关系变化、道具铺垫、信息揭示可能被压缩为一个“主事件”。
- **错误改编依据被层层放大（R）**：改编指引、故事大纲、集纲和剧本都消费同一个不完整事件表，早期遗漏会成为全流程遗漏。
- **无法精确审计忠实度（R）**：审核只能说“似乎偏离原文”，无法指出对应原文位置和变更链。
- **长篇小说后期风险更高（R）**：章节数量越多、单章越长、人物线越复杂，信息损失越严重。

#### 典型生产症状

- 编剧说“这一段原文里明明有，为什么大纲没写”；
- 角色提前知道秘密，或忘记已经发生的事件；
- 道具和人物在前文出现、后文却没有回收；
- 后期需要重新人工搜索原文并补回关键情节。

#### 业务待确认

- Fangcun 当前主要处理多少章、每章平均多长的小说？
- 业务更重视严格还原、保留主干，还是允许高自由度重构？
- 编剧现在是否会人工检查事件表？如果会，通常检查到什么粒度？

### 4.3 用户需求确认与项目 Rules

#### 当前设计

用户提出集数、时长、平台、风格、改编要求；系统生成 S0 需求文档，并通过项目 Rules 持续记录后续修改要求。

#### 已确认问题

1. **用户原始需求和 AI 归纳结果没有结构化差异记录（C）**。

2. **项目规则要求所有产物末尾添加“项目规则落实清单”（C）**，但剧本 Prompt 明确要求只输出剧本 XML、禁止清单或解释。

3. **Rules 同时混合创作要求、平台规则和工作流治理要求（C）**，主要依赖自然语言优先级解释，而不是字段化约束。

4. **规则变更缺少明确的影响范围编译（C）**  
   当前规则会进入后续上下文，但没有清楚表达“从第几集起生效、是否回改历史产物、影响哪些人物或阶段”。

#### 生产影响

- **需求被二次解释（R）**：AI 归纳后的 S0 可能把用户模糊意见升级为硬规则，或遗漏语气中的优先级。
- **同一要求重复沟通（R）**：当规则没有落实到具体集和具体产物，编剧需要多次提醒。
- **规则污染（R）**：关于 Fangcun 优化、飞书治理或其他项目的讨论，若误进入创作 Rules，可能影响剧本内容。
- **历史版本返工范围不清（R）**：用户修改角色、题材或节奏后，团队不知道应该只影响新批次，还是回改大纲和已完成剧本。
- **格式死锁（R）**：模型不输出清单会被 Rules 校验判错；输出清单又违反剧本纯正文要求。

#### 业务待确认

- 实际项目中，需求最常在哪个阶段发生变化？
- 哪些要求必须追溯修改全部历史产物，哪些只对后续生效？
- 谁拥有最终规则解释权：编剧、主编、制片还是客户？

### 4.4 改编指引、故事大纲与集纲

#### 当前设计冲突

根 Skill 规定：

`改编指引 → 新故事大纲 → 集纲 → 剧本`

真实 `_run_all()` 执行：

`S0 需求 → S1 故事骨架/集纲 → S2 改编策略 → 剧本`

`story_outline` 在代码中被标为旧版兼容，不进入真实全流程。

#### 已确认问题

1. **阶段顺序存在三套不同定义（C）**：根 Skill、Drama Skill 和 pipeline 不一致。

2. **改编子技能和监督子技能的同名 Prompt 被 drama 目录优先遮蔽（C）**。

3. **集纲在改编策略之前先成为“全剧结构事实源”（C）**。

4. **`skeleton.md` 一方面宣称基于故事大纲，运行时却主要读取 S0 和事件表（C）**。

5. **多个可选创作技法在自检部分又被当成必选项（C）**。

#### 生产影响

- **创作决策因果倒置（R）**：在明确“怎么改”之前先锁定故事结构，改编策略只能为既有骨架补理由。
- **用户审核对象和系统真实上游不一致（R）**：用户以为批准了改编指引再进入大纲，系统可能已经先生成骨架。
- **已否决思路污染下游（R）**：错误顺序下，下游文件可能沿用用户尚未批准或根本没见过的设定。
- **过程资产失去独立价值（R）**：故事大纲原本可用于投流、立项和商业讨论，但在真实主流程中被降为兼容文件。
- **不同入口得到不同结果（R）**：同一项目用 `--phase` 单步和用 `--phase all`，可能走出不同的逻辑路径。

#### 业务待确认

- 业务中的“改编指引、故事大纲、集纲”各自由谁使用、解决什么决策？
- 哪一阶段是客户或主编真正愿意花时间确认的高价值节点？
- 集纲是否必须包含逐集原文章节依据、场景、情绪、付费点和钩子？

### 4.5 单集剧本生成

#### 当前设计

系统按批次逐集写草稿，输入包括项目需求、项目 Rules、骨架片段、改编策略、事件表、上一集剧本、原文片段和连续性状态。

#### 已确认问题

1. **每集事件表只取全局 `events_text` 的前 2000 字（C）**  
   后期集数仍可能主要看到开篇事件。

2. **原文片段按章节数平均分配给剧集（C）**  
   没有读取集纲中该集真正使用的章节或事件 ID。

3. **原文最多采样 5 章，每章 2500 字，最终整段又截为 3000 字（C）**  
   实际可能只保留第一章的大部分内容。

4. **20 集以内的集纲详情可能提取失败（C）**  
   解析器更可靠地支持表格行或包含“详情”的标题，而 Prompt 的常见标题是 `### 集N：...`。

5. **时长/字数标准冲突（C）**  
   项目信息和 Prompt 使用约 150 字/分钟，运行时生成和校验使用约 500 字/分钟。

6. **剧本格式冲突（C）**  
   Prompt 接受“晚”和 `V.S.`，校验器只接受另一组时间标签并主要识别 `VO/OS`；对于台词情绪括注，也同时存在“尽量每句标注”和“括注过多是新手问题”。

7. **每集全量加载大 Prompt（C）**  
   `script_local.md`、writing-methods 和全部 craft 文件都会被加入系统 Prompt，即使说明文字声称应按需加载。

#### 生产影响

- **后期集数事实错位（R）**：模型根据开篇事件或错误章节续写，出现跨集穿越、重复剧情或无依据原创。
- **集纲落实率降低（R）**：即使集纲设计正确，Writer 可能没有拿到该集的完整 contract。
- **剧本越来越模板化（R）**：爆、虐、爽、3-15-45、强反转等方法同时高权重出现，会让不同题材趋向相同节奏和表达。
- **模型注意力被格式和自检占用（R）**：上下文越大，真正项目事实在总上下文中的权重越低。
- **“看起来很像短剧”但不属于这个项目（R）**：形式合格、钩子明显，却可能失去原作人物、关系和独特气质。
- **字数门禁误伤或放过（R）**：团队对“一分钟应该写多少”没有统一口径，产物可能在不同阶段被相反标准判断。

#### 典型生产症状

- 前几集尚可，越往后越偏；
- 角色台词声音趋同；
- 集集都在打脸、反转、卡断，但整部剧没有真正递进；
- 编剧需要把本集原文和集纲重新粘贴给模型；
- 格式修改花费超过内容修改。

#### 业务待确认

- 当前最不满意的是忠实度、戏剧性、台词、节奏、人物还是可拍性？
- “效果好”的判断来自编剧、客户、投流数据还是成片表现？
- 当前是否存在可代表“好结果”和“差结果”的真实剧本批次？

### 4.6 AI 审核、人工确认与返工

#### 当前设计

阶段文件生成后进行 AI 审核，再等待用户明确确认；剧本草稿还具有单集复审和定向重写。

#### 已确认问题

1. **上游审核门禁主要检查审核文件是否存在且大于一定长度（C）**，并不稳定解析报告是否真正通过。

2. **人工确认接受任意 decision 字符串（C）**  
   即使 decision 表达 rejected，也会清空 pending 状态。

3. **完成阶段默认直接跳过（C）**  
   输出提示说可用同一 `--phase` 强制重跑，但 `_run_phase()` 没有真正的 force 逻辑。

4. **状态机阶段表缺少 requirements 和 story_outline（C）**，与当前 `_run_all()` 不一致。

5. **创作和审核未形成真正独立信息环境（C）**  
   当前更多是更换 Prompt 的再次模型调用，而不是证据隔离、角色隔离和可追踪的专项批评。

#### 生产影响

- **拒绝不等于阻断（R）**：用户或主编已经否决，但系统状态可能允许继续生成下游内容。
- **返工需要手工改状态或改文件（R）**：用户说“重做大纲”时，系统可能认为阶段已完成而跳过。
- **审核看似完整但缺少可执行定位（R）**：A/B/C/D 评分容易给出概括性建议，却不能定位到事件 ID、场景或原文依据。
- **同源偏见（R）**：Writer 和 Reviewer 共享相似方法论时，审核更容易确认自己的套路，而不是发现创作方向本身有问题。
- **人工审核疲劳（R）**：每个阶段都停，但部分停顿只是格式或交付确认，真正高价值决策被大量低价值确认稀释。

#### 业务待确认

- 目前谁看审核报告？是否真的根据报告做决定？
- 人工通常回复“确认”，还是会给出具体修改意见？
- 最常返工的是整阶段重做，还是局部 patch？

### 4.7 飞书交付与项目资产管理

#### 当前设计

每阶段必须创建在线文档、验证正文、在主群回贴链接并等待确认；剧本按批次交付，最终汇总需用户明确触发。

#### 已确认问题

1. **主 pipeline 不会自动调用飞书同步器（C）**。

2. **`build_feishu_project.py` 默认只生成 manifest（C）**，必须显式传入 `--execute` 才实际创建在线内容。

3. **本地阶段完成、飞书同步完成、群里回贴成功分别由不同逻辑负责（C）**，没有统一事务状态。

4. **固定表格规范和执行器实现存在字段/行差异（C）**。

5. **每次同步会创建版本化文档（C）**，但创作阶段没有统一 content hash/idempotency 流程来判断内容是否真的变化。

#### 生产影响

- **本地完成但业务看不到（R）**：技术上已有文件，群里却没有链接，业务认为任务失败或仍在运行。
- **在线版本滞后（R）**：编剧修改了本地脚本，但飞书仍是旧版本。
- **重复文档和版本选择成本（R）**：反复同步可能产生多个近似版本，用户不知道哪个是当前推荐稿。
- **门禁状态失真（R）**：本地 `state.json` 标记完成，不代表在线文档可打开、正文存在或群内已交付。
- **跨角色协作困难（R）**：主编、编剧、运营和客户可能分别在本地、群消息和飞书文档看到不同状态。

#### 业务待确认

- 飞书是正式生产系统，还是仅用于查看和交付？
- 谁负责确认“当前推荐版本”？
- 是否真的需要每阶段都创建新文档，还是某些阶段只需更新同一文档版本？

### 4.8 Token、成本、质量与运营观测

#### 已确认问题

1. `drama_observer.py` 支持 usage，但 pipeline 调用 API 时没有按示例请求 `return_usage=True`（C）。
2. 阶段统计默认写入 `total_tokens=0`（C）。
3. ROADMAP 引用的部分 token 事件文件在当前仓库中不存在（C）。
4. 项目 ID 推导可能把多个项目记为 `output`（C）。
5. 当前测试主要保护格式和局部工作流，没有覆盖真实创作质量、上下文正确性和飞书完整闭环（C）。

#### 生产影响

- 无法知道哪一阶段最贵、哪一种返工最耗 token；
- 无法比较不同模型在忠实度、戏剧性和首轮通过率上的投入产出；
- 无法判断 Prompt 变长后，质量是否真的提升；
- 无法证明新版 Skill 超越旧版，只能依赖主观印象；
- 多项目规模化后，预算和产能难以预测。

## 5. 跨流程影响链

### 影响链 A：原文事实损失

`章节后半段未进入事件表 → 改编/大纲缺少关键事实 → 集纲没有分配 → 剧本无依据原创 → 审核无法定位原文证据 → 编剧人工补回`

最终损失不是一次事件提取失败，而是后续所有阶段的复合返工。

### 影响链 B：流程顺序冲突

`系统先生成骨架 → 用户以为先审核改编指引 → 用户修改改编方向 → 已有骨架需要推倒 → state 又认为阶段完成 → 人工改文件/状态后重跑`

最终表现为：流程明明设置了很多门禁，却仍不能保护高价值决策。

### 影响链 C：当前集上下文错配

`Writer 收到事件表开头 + 平均分配章节 + 不完整集纲片段 → 写出形式合格但事实错误的剧本 → 格式门禁通过 → AI Reviewer 重点检查短剧方法 → 原作偏离进入正式批次`

这是当前最可能直接影响剧本内容质量的链条。

### 影响链 D：规则冲突

`用户新增项目 Rule → 系统要求末尾清单 → 剧本 Prompt 禁止清单 → 模型随机选择服从对象 → 校验失败或正文夹带元信息 → 返工`

### 影响链 E：交付状态分裂

`本地文件完成 → state 标记 done → 飞书未 execute/写入失败 → 群里无链接 → 用户重复催促或重新触发 → 产生重复版本`

## 6. 风险优先级

### P0：在扩大生产前必须解决

| ID | 问题 | 主要损害 |
|---|---|---|
| P0-01 | 没有唯一阶段顺序和产物契约 | 错误流程、返工和下游污染 |
| P0-02 | 当前集事件、原文和集纲上下文错配 | 直接降低剧本内容质量 |
| P0-03 | 事件表缺少完整事件和原文证据 | 忠实度、连续性和审核不可追溯 |
| P0-04 | Prompt、Rules、validator 冲突 | 随机失败、格式返工、模型困惑 |
| P0-05 | 人工拒绝与重跑语义不完整 | 已否决版本继续推进 |
| P0-06 | 本地创作与飞书交付状态分裂 | 交付失败、版本混乱、用户不信任 |

### P1：决定效果上限和规模化能力

| ID | 问题 | 主要损害 |
|---|---|---|
| P1-01 | 全量巨型 Prompt 与套路堆叠 | 题材趋同、项目事实权重下降 |
| P1-02 | 伪多 Agent、审核缺少独立性 | 难以发现方向性错误 |
| P1-03 | 初始化配置与运行契约不一致 | 新项目假成功、人工介入 |
| P1-04 | 状态机和实际阶段不一致 | 断点恢复错误 |
| P1-05 | 资产缺少统一版本图和内容哈希 | 重复版本、难以局部修订 |
| P1-06 | token 和项目归因失真 | 无法控制成本和评估升级价值 |

### P2：可在主链稳定后处理

- 安装和分发路径统一；
- Python 版本声明与实际语法兼容；
- 表格模板细节一致性；
- 翻译、完整 Dashboard 和更多外围资产能力。

## 7. 当前版本不应被误删的能力

升级时必须保护以下已产生生产价值的机制：

1. 剧本草稿和正式版本分离。
2. 单集局部重写，不全量覆盖整部剧。
3. 剧本批次确认后才提升正式稿。
4. 连续性状态和上一集承接。
5. 确定性格式/分场门禁。
6. 项目 Rules 的版本化思想。
7. 项目和 bot/chat 绑定保护。
8. 飞书文档永久保留旧版本。
9. 最终汇总必须由用户明确触发。

换言之，新版应该重构“流程真相、上下文和质量判断”，而不是丢掉现有的生产控制能力。

## 8. 真实业务中需要补齐的数据

为了判断哪些问题最值得先改，建议后续从真实项目收集以下最小数据：

| 数据 | 用途 |

| 一个返工严重或失败的项目 | 还原问题发生链，而不是只看最终差稿 |

| 审核意见和用户确认记录 | 判断门禁是否产生实际价值 |
| 每阶段耗时、重跑次数、模型和 token | 估算真实生产成本 |
| 最终成片或投流反馈（如有） | 建立“文本质量”和业务效果之间的关系 |

## 9. 后续需求访谈顺序

后续不建议直接讨论目录、Agent 数量或模型选型。应依次确认：

1. **使用背景**：Fangcun 服务谁、解决什么任务、最终交付给谁。
2. **真实流程**：从项目进入到剧本/成片交付，人员、输入、确认和返工如何发生。
3. **效果定义**：什么叫好剧本，谁有最终判断权，有没有可比较样本。
4. **原文与改编边界**：不同项目需要多高忠实度，允许改到什么程度。
5. **阶段价值**：改编指引、大纲、集纲分别解决什么业务决策，哪些必须人工确认。
6. **单集生产**：Writer 真正需要哪些输入，最常见失败是什么。
7. **审核与修改**：问题如何定位、如何局部改、谁确认生效范围。
8. **交付与协作**：飞书在业务中的真实角色、版本和权限要求。
9. **规模与成本**：项目数量、集数、并发、时效、预算和稳定性要求。
10. **评测基线**：选择哪些历史项目证明新版确实优于当前版本。

每完成一项访谈，应产出四类结论：

- 业务事实；
- 当前痛点及频率；
- 不可破坏的现有能力；
- 新版验收标准。

在以上内容确认前，不应锁定最终技术架构。

## 11. 第一轮业务访谈记录：背景、演变与当前目标

### 11.1 已确认的业务背景

1. Fangcun 最初是部署在 Agent 上的小说仿写 Skill，并非从零为专业短剧生产设计。
2. 与公司合作后，目标改为“小说转短剧剧本 Skill 系统”。
3. 公司采用本地部署在租赁服务器上的 OpenClaw 架构：
   - 一个主 bot 管理多个子 bot；
   - 每位编剧老师配置一个子 bot；
   - 子 bot 与飞书生态打通，并拥有完成项目协作所需的飞书权限；
   - 编剧老师创建项目群，在群内与 bot 对话、安装和使用 Skill；
   - 各阶段产物同步到飞书文档；
   - 产品老师可以创建自己的 bot，或在管理群通过主 bot 管理所有子 bot。
4. 公司当前希望的核心创作顺序是：

   `改编指引 → 故事骨架 → 集纲 → 剧本`

   其中改编指引仍以原小说故事为主，只根据编剧需求微调整体情节，使其适合短剧表达。
5. 原始小说仿写流程是：

   `故事骨架 → 改编指引 → 集纲 → 剧本`

   合作伙伴曾尝试修改流程顺序，但没有完成彻底迁移，这与代码中仍存在的多套流程定义相互印证。
6. 后续逐步加入：
   - 每阶段 AI 审核报告；
   - 人工确认后进入下一阶段；
   - 每个阶段允许反复修改；
   - 集纲到剧本的 API 并行生成；
   - 为降低编剧配置门槛而增加 Agent 模式；
   - 飞书统一产物可见性；
   - 项目状态记录。
7. token 和总体进度的跨 bot 汇总由另一个 Skill 扫描完成，不属于本轮 Fangcun 创作主链优化重点。
8. 当前明确的升级目标是：暂不优先处理统计系统，先保证真实使用流程中的创作效果和生产效率。

### 11.2 已确认的产品问题

问题主要集中在集纲和剧本阶段：

1. Fangcun 经常自行改编，不够贴合原文；存在原小说仿写遗留逻辑继续污染当前流程的可能。
2. 台词过于简陋，前后承接弱，人物行为和剧情缺少因果关系。
3. 剧本不严格执行已确认集纲，模型会脱离集纲自由发挥。

这些现场反馈与代码分析发现的事件表信息损失、当前集上下文错配、集纲片段提取不稳定和巨型通用 Prompt 高度相关，但尚需通过真实项目逐条定位：问题最早是在事件提取、改编指引、故事骨架、集纲还是 Writer 阶段出现。

### 11.3 已确认的真实使用方式

原设计假设是：

`全量集纲完成并确认 → 按批次生成剧本`

实际生产中，部分编剧老师采用：

`2 集集纲 → 2 集剧本 → 修改 → 下一小批次`

修改入口包括：

- 在项目群内直接与 LLM 对话修改；
- 在飞书产物文档中写批注，让 LLM 读取批注后修改；
- 编剧直接人工重写某一版本，再上传作为新版本。

当前典型剧本单集可能迭代 7～8 个版本。原计划一天完成一本，实际需要 7～8 天。

### 11.4 对此前诊断的关键修正

#### 修正一：“没有按标准流程使用”不应先归因于用户

编剧老师的微批次生产和高频人工修改，可能是对当前产品质量不足的适应性行为，而不是单纯的执行不规范。若强迫编剧回到原来的全量瀑布流程，而没有先改善集纲和剧本质量，可能只会增加等待和一次性返工规模。

#### 修正二：当前系统的真实矛盾是工作模式错配

Fangcun 最初按“AI 主导、人类阶段验收”的模式设计：

`AI 批量规划 → AI 批量生成 → 人工确认或微调`

实际生产已经演化为“编剧主导、AI 高频协作”：

`编剧提出局部方向 → AI 生成小批次 → 编剧深度修改 → AI 再生成 → 人工终稿`

Fangcun 当前的状态、集纲和上下文机制仍服务前一种模式，因此无法可靠吸收后一种模式产生的大量修改。

#### 修正三：可能存在“低质量—绕流程—上下文冲突—更低质量”的恶性循环

当前最值得验证的生产影响链是：

`初始集纲/剧本效果不佳`

`→ 编剧不再信任全量集纲，改为 2 集集纲 + 2 集剧本`

`→ 修改散落在群聊、飞书批注、人工上传稿和不同版本中`

`→ 已确认集纲、旧剧本、项目 Rules 与人工最新版可能同时存在`

`→ Fangcun 无法判断哪个是当前事实源，也不知道修改是否应回写集纲`

`→ 下一集继续读取过期或冲突信息`

`→ 前后不接、因果断裂、偏离集纲，触发更多人工修改`

这条链目前有明确的业务现象支持，但“具体在哪个文件和调用阶段发生冲突”仍需用真实项目验证。

### 11.5 当前最核心的业务问题已经变化

此前可以把问题描述成“怎样让 AI 按标准瀑布流程生成完整短剧”。

结合真实业务后，更准确的问题是：

> 怎样让 Fangcun 在编剧主导、允许小批次迭代和人工深度改稿的真实生产方式中，始终知道当前有效版本、原文依据、已确认集纲、最新修改意见及其影响范围，并稳定生成贴合原文、服从集纲、前后因果连贯且台词达到专业要求的剧本。

这意味着未来设计必须同时回答两件事：

1. 如何提高第一次集纲和剧本输出的质量，减少进入 7～8 轮返工；
2. 当人工修改不可避免时，如何让修改成为新的正式事实源，而不是与旧集纲、旧剧本和聊天记录并存冲突。

### 11.6 暂不纳入本轮核心范围

根据当前业务优先级，以下内容暂不作为第一阶段升级重点：

- 主 bot 对全部子 bot 的 token 汇总；
- 全公司统计和管理看板；
- 复杂成本归因；
- 与创作效果无直接关系的外围表格优化。

这些能力应与 Fangcun 创作引擎保持清晰接口，但不应继续堆入当前核心 Prompt 和创作流程。
