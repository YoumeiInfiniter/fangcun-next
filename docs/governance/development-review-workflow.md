# Fangcun Next 开发与独立评审协作机制

> 适用范围：Fangcun Next 的开发、技术验收、内容质量测试和 OpenClaw 试点。
> 目的：让产品负责人、开发实施模型和独立评审模型使用同一套职责、证据与放行标准。

## 1. 核心原则

1. 用户是产品负责人和最终内容作者代表，负责业务决定与内容质量判断。
2. 开发模型负责实现、实现级测试和诚实交接，但不能自行宣布独立验收通过。
3. 独立评审模型负责只读复审、外部反例和隐藏变体，并给出技术放行结论。
4. 技术可靠性与剧本内容质量分开验收。测试全绿不证明剧本好；好案例也不能掩盖状态、版本或证据漏洞。
5. 脆弱且可确定判断的规则必须落实为代码、Schema 和测试，不依赖 Prompt 自觉。
6. 仓库是事实来源。长期规则、当前合同、实现和测试均需版本化，聊天提示词只负责导航和启动。

## 2. 三方职责

### 2.1 用户：产品负责人

用户负责：

- 决定产品目标、编剧工作方式和优先级；
- 决定哪些真实小说、集数和编剧终稿用于质量测试；
- 判断原文贴合、集纲遵循、因果、台词、人物认知和可用性；
- 本地质量测试通过后，决定是否进入 OpenClaw 小规模编剧试点；
- 提供真实反馈并决定下一轮产品需求。

用户不需要判断哈希、状态机、版本指针、不可变快照或路径完整性等底层实现。

### 2.2 开发实施模型

开发模型负责：

- 完整读取 `AGENTS.md`、规格书、当前修复合同和上一轮交接；
- 在指定分支和起点后实施，不重写历史；
- 将修复落实为通用不变量，不针对固定夹具硬编码；
- 编写实现级单元测试并运行完整回归；
- 提交代码和交接文档，报告实际命令、数量、失败、跳过、API 使用和限制；
- 发现规格冲突时停止相关扩展并报告，不自行放宽安全要求。

开发模型不得：

- 把自写测试全绿称为“独立验收通过”；
- 删除、跳过、弱化或反向修改外部验收案例；
- 为通过测试识别固定项目名、路径、ID、哈希或夹具内容；
- 未经授权修改生产版、合并 `main`、写入飞书或调用真实线上能力。

### 2.3 独立评审模型

独立评审模型默认只读，负责：

- 从指定 commit 和干净工作区复现开发方测试；
- 检查实现，不只阅读交接自述；
- 使用临时项目独立构造反例；
- 在公开案例之外改变路径、内容、顺序、版本和篡改方式；
- 对照规格书验收项给出证据、严重度和放行结论；
- 将失败描述成可复现行为和通用不变量，交回开发模型修复。

独立评审模型在用户未明确授权时不修改代码、不合并分支。

## 3. 单轮协作生命周期

每一轮固定执行：

1. 独立评审模型只读发现问题，形成问题清单和外部反例。
2. 将问题固化为 `docs/development/independent-review-roundN-fix-brief.md`。
3. 用户用短启动提示词要求开发模型读取合同并实施。
4. 开发模型修复、运行全部测试、提交 commit，并生成 `fix-handoff-roundN.md`。
5. 用户把最终 commit 和复审入口交给独立评审模型。
6. 独立评审模型从干净状态复现公开测试，再运行未公开变体。
7. 按第 5 节给出红灯或黄灯；内容测试和试点阶段再使用绿灯。

禁止仅在聊天中维护重要合同。每轮可变要求写入当轮 fix brief，长期要求写入本文件或规格书。

## 4. 测试所有权与防自证机制

### 4.1 开发者测试

开发模型可以自由增加单元测试、集成测试和回归测试，用于证明实现符合自身设计。开发者测试是必要证据，但不是独立验收。

### 4.2 公开外部验收案例

公开外部验收案例由独立评审模型提出，写入当轮 fix brief。开发模型可以看到输入、操作和预期，以便修复已知问题，但不得改变其业务含义。

若既有测试与上位规格确实相反，只能在当前 fix brief 明确点名后修改，并在 handoff 记录修改前后行为和理由。

### 4.3 隐藏变体

隐藏变体不提前写入开发分支。独立复审时基于相同不变量临时改变：

- 项目名、临时目录、文件名和路径形式；
- 版本数量、操作顺序和中断恢复位置；
- 跨项目引用、文件篡改和指针组合；
- 空字段、非法字段、边界值和哈希前缀；
- 单集、小批次、整批替换和历史恢复。

隐藏变体用于判断实现是否修复通用规则，而不是只覆盖公开样本。

### 4.4 完整回归

每次修复除运行当轮案例外，还必须运行：

- 新版 unit；
- 全部 regression；
- smoke；
- EP001 回归；
- 旧版行为基线。

局部测试通过不能替代完整回归。

## 5. 放行信号

### 红灯：技术基础不可信

满足任一项即为红灯：

- 存在可复现的 Critical/High 状态、版本、路径、审核、证据或连续性漏洞；
- 关键门禁可以绕过；
- 错误状态会静默继续并污染后续产物；
- 外部验收或隐藏变体失败；
- 开发结果无法从干净状态复现。

红灯时不得进入用户内容质量测试。

### 黄灯：可以开始本地内容质量测试

同时满足以下条件才能给黄灯：

- 没有已知阻断级技术问题；
- 公开外部案例和隐藏变体通过；
- 完整回归没有新增失败；
- 干净项目的核心生命周期可运行；
- 剩余限制已记录，且不会造成静默错误或错误定稿；
- 分支、commit、交接和工作区状态明确。

黄灯只证明技术候选版本可用于用户测试，不证明剧本质量达标。

### 绿灯：可以进入 OpenClaw 编剧试点

绿灯由用户在黄灯后决定，至少要求：

- 用户用多种代表性案例完成本地质量测试；
- 剧本达到用户认可的基本可用水平；
- 内容问题可以被定位和复现；
- 先进入少量项目或少量编剧试点，而非直接全量推广。

## 6. 技术收敛策略

- 一轮修复后出现新的不同边界问题，可以继续按合同收敛。
- 若连续多轮反复出现同一类状态或绑定漏洞，停止叠加补丁，改为简化或重构相关状态核心。
- 技术黄灯后停止无限加固，转入真实内容测试；内容反馈不能用纯格式测试代替。
- 内容测试阶段发现确定性 Bug，重新进入本流程；发现创作质量问题，另建产品/质量改进合同，不混入底层安全修复。

## 7. 文档与提示词分工

### `AGENTS.md`

只保存长期、全仓适用的规则和文档地图，保持简短。

### 规格书

`docs/specs/fangcun-next-design-spec.md` 是产品与架构唯一设计基线。

### 当轮 fix brief

只保存当前轮次的问题、修复不变量、公开验收案例、范围和完成定义。

### 当轮 handoff

只保存开发后的实现事实、commit、测试和限制，不能替代独立验收。

### 启动提示词

启动提示词只应包含：角色、仓库、分支、起点、必读文件、当前动作、禁止事项和交付入口。不要重复粘贴规格书或 fix brief 正文。

## 8. 开发交接最小字段

每轮开发交接必须包含：

- 起点 commit、全部新增 commit 和最终 HEAD；
- 问题到修改文件、通用不变量和测试编号的映射；
- 完整测试命令、数量、通过、失败和跳过；
- 是否使用真实模型/API、是否执行平台写入；
- 与旧版兼容性变化；
- 已知限制和最高风险文件；
- 给独立评审模型的简短只读复审入口。
